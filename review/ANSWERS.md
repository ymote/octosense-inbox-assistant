# App Hub review answers

Publisher preparation for `org.octosense.samples.inbox` `0.1.0`. These answer
the **eight questions actually emitted** by the matching `hub scan`, not an
older seven-question template. Scan packets stay in ignored `build/`.
This document is not a reviewer approval.

## 1. Does the app do what its name, subtitle and description claim? Cite the text in its source.

The listing claims a developer preview, not validated live Gmail delivery. [`src/workspace.splash`](../src/workspace.splash) implements `connect` through `auth.connect`, `refresh`/folder reads through `gmail.messages` and `gmail.message`, `persist` through revisioned `gmail.draft.edit`, `ask` through `octos.session.open` and `octos.turn.start`, and `review` through `gmail.draft.review`. Reply and Chat reload one host draft. `publish` uses the admitted Glance workspace. [`bundle/AGENT.md`](../bundle/AGENT.md) and its [triage skill](../bundle/skills/incoming-mail-triage/SKILL.md) describe new-message relevance and require durable quiet/published receipts. The host collector is native runtime code, not generated by declaring a trigger.

Historical functional source passed 33 Mac soak cycles and cold restoration with real DeepSeek plus synthetic Gmail. Two frame-submission errors remain unresolved. Live OAuth/read/send and physical approval are unverified. Publisher/listing changes create a new package digest; those historical runs are not claimed as tests of this new signed package. See [provenance](../ATTRIBUTION.md).

## 2. Do the listing's platforms and category fit an app of this kind?

`productivity` matches an email reading/reply workflow. Only `macos` is listed. Historical tests used a native hidden macOS Shell and Makepad input, not Android, Windows or Linux. Android Google authorization is missing. The listing requires OctoSense #347 and App Hub #119 and does not imply broad released-host support.

## 3. Do the granted capabilities match what the app visibly does? For a script app, name every host it requests and why. Name any grant nothing on screen needs.

All seven requested capabilities have a visible or declared role: `storage` stores fictional drafts/selected handle; `auth` opens host Google login and disconnects; `gmail` reads messages and manages authoritative reply/review state; `model` serves the explicit AI sort action; `glance` pins/publishes/retires local cards; `octos.session.open` and `octos.turn.start` serve Chat and the app peer. `storage.accounts:true` supplies account-scoped workspace binding. The declared background `inbox.new_message` trigger and `ask_user_question` tool support the consented peer, not an unattended send.

The app requests **no direct network hosts and no `net` capability**. Google OAuth/Gmail requests and model-provider calls are delegated to host services under their own checks. The bundle contains no publisher backend URL in executable code. No unused grant was identified in this review; credentials remain with the host.

## 4. Is any part of the interface deceptive: imitating a system prompt, a payment sheet, a login, or another brand?

The app names itself Inbox Assistant and labels the offline data fictional. Its Connect Google button requests the actual host authentication sheet; it does not imitate a Google password form or collect credentials. Review & Send requests a native host sheet; the application does not forge an approval. Provider names describe compatibility, not affiliation. There is no payment interface.

## 5. Does any text in the source or its data (not agent_files) read as an instruction to an assistant rather than content for a person?

Yes, intentionally scoped model prompts exist in application source: `ask` constructs instructions for this app’s own account-bound peer, and `classify` supplies a bounded task/schema to `model.complete`. These are developer-authored host requests, not displayed email instructions or a request for a reviewer/system agent to bypass rules. The original message is supplied as data, with explicit untrusted-mail boundaries. Fictional fixture prose describes messages and never authorizes sending. The reviewer should distinguish these expected prompts from malicious instructions arriving in a real email.

## 6. Is any wording abusive, or aimed at a private individual?

No abusive wording or attack on a private individual was identified. Included senders, appointments, addresses and screenshots are fictional examples using reserved example domains. No personal email, credential, private account record or raw runtime conversation log is distributed.

## 7. The agent files (agent_files) instruct this app's own assistant. Do they stay within this app's data and tools, without addressing other apps' assistants or the system agent, or asking for tools, hosts or approvals the manifest does not grant? Does each tool's risk match what it does: anything that sends, posts, shares, deletes or spends must be destructive; is anything marked shareable that returns the person's private data? For a tool with confirm "app", does the app visibly show its own confirmation, with the exact action, before it runs?

The declared AGENT and skill remain within this app/account. They require exact host-supplied identity, treat email as untrusted, read back saved edits, prohibit autonomous sending and reject invented Calendar or memory capabilities. Mentioning that cross-app booking requires a real separately granted tool does not request or install that tool. The skill contains text/data only.

All nine [`inbox.*` tools](../bundle/tools.json) are `private_data:true` and `shareable:false`. Message/draft/event reads have `read` risk. Draft creation/edit, durable decisions and local Glance publish/withdraw use `act`; these change local account state or local display, not remote mail or public sharing. Withdraw retires a card rather than deleting a Gmail message. No tool sends, posts remotely, deletes provider data or spends. No `confirm:"app"` tool is declared. Sending is exclusively the UI-to-host immutable native review path with physical provenance; a model, script, service-origin flag or instrument click cannot approve it.

Agent consent enables model triage of eligible new mail before importance is known. Thus quiet messages can still reach the configured model. The [privacy policy](../PRIVACY.md) explicitly discloses this, along with local records, notification visibility and incomplete deletion limits.

## 8. Route: pass, human-review, or reject. Give reasons a publisher can act on.

**Recommended route: human-review.** This is an author preparation report, not an App Hub reviewer verdict or approval. The unsigned structural gate passes, but the package depends on connected-services runtime/Hub changes, live Google and actual sending remain unverified, and the Mac instrument had two unresolved frame-submission errors. A maintainer must verify the published tag/commit, publisher signature, live privacy/support URLs and compatibility before deciding catalog admission. Only macOS developer-preview scope is proposed. Do not silently upgrade this to a stable/live-provider release or add Android. Root publication tooling supplies final signed gate and release metadata separately.
